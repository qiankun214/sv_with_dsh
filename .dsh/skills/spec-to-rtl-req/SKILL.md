# ① 功能点

产出**一份** `01-requirements/REQ-<nnn>-<slug>.md`，它是整条追溯链的源头，必须可被下游逐条引用。

## 写文档前：先调用 `grill-me` 讨论

**任何阶段文档（REQ / ARCH / DES / VP / CHK）动笔前，先用 `grill-me` 技能与用户做一轮质询式讨论**，
把边界、取舍、待定项问清楚，再落成文档。做法：

1. 自己先把仓内事实查清（模板、上下游产物、门禁规则、已有约定），不要把能查到的事拿去问用户；
2. 加载 `grilling` 技能并按其执行：**每轮用一次 `ask_user_question`**，把该轮的决策点做成卡片
   （每项一个稳定 `id` 与短 `header`，推荐项放第一并标注「（推荐）」+ 一句取舍说明）；
3. 讨到「没有未决问题、且用户确认理解一致」为止；结论写进文档的正文/变更历史，**不要**把讨论过程抄进产物；
4. 讨论中出现的规范级结论（新的写作/结构约定）要回流到本技能或模板，别只留在当轮对话里。

## 本仓固化的写作约定（历次评审反馈沉淀，逐条都是硬要求）

- **章节顺序固定**：背景与目标 → 功能描述（F*）→ 软硬件接口 → 硬件接口 → 约束 → 验收标准（AC 判据表）→
  non-goals → 变更历史。
- **软硬件接口先给结论**：无软件接口 → 一句结论 + 软件还能通过什么影响本模块 + 「要加须另立 `REQ-*`」边界
  （**不要**列全「无」的表）；有软件接口 → 详细描述（寄存器/总线/中断/地址空间/访问属性 + `REGMAP-*`）。
- **硬件接口三段式**：① 参数表；② 接口信息（表头固定 `端口/方向/位宽/时钟域/复位值/含义`；用到结构体才加成员表）；
  ③ 接口协议——**只写接口**：输入侧/输出侧/握手/复位/时钟 + 接口不变式。**不得**写内部实现与功能映射
  （状态机、指针/计数器、算法、公平性推导、「给什么输入出什么输出」的功能解释），**不得**写组合路径延迟数字。
- **时序图只画端口信号**，不含内部状态；一场景一对 `scenario-N-<场景名>.json` ↔ `.svg`，
  放 `01-requirements/<本 REQ 文件名去扩展名>/`（与 md 同名、同级的目录），两件都入 `artifacts`。
  每个场景固定为「WaveDrom 图 + 文字说明（接口口径）」，需要时加一张**只列端口信号**的逐拍表。
- **F 与 AC 分工**：F 是行为契约；AC 是判据表（覆盖 F / 激励 / 观测点 / 量化判据），不得复述 F 的行为。
- **返工要留痕**：内容变更即作废原放行（`approved` → `in_review`，清空 `reviewer`），并在变更历史写清改了什么、
  为什么改、影响哪些上下游。
- **不得自行放行**：`reviewer` 只能是真实人类；样例数据必须显式标注为样例评审。

## 步骤

```bash
python3 tools/sv.py new req --title "时钟域划分" --slug clk-domain
```

然后填写正文。写作要求：

| 小节 | 硬要求 |
|---|---|
| 功能描述 | 逐条编号（F1/F2…），每条是可验证的行为，不写「高性能」「灵活」这类不可判定词 |
| 软硬件接口 | 先给结论。**无软件接口就只写一句结论** + 软件还能通过什么影响本模块（通常是综合期参数）+ 「要加软件接口须另立 `REQ-*`」的边界，**不要列一张全「无」的表**；**有软件接口才详细描述**（寄存器/CSR、总线从接口、中断、地址空间与访问属性，并指向 `REGMAP-*`） |
| 硬件接口 | **固定三段式**：① 参数表（默认值 + 合法范围）；② 接口信息（端口表表头为**端口/方向/位宽/时钟域/复位值/含义**；用到结构体时再加「成员/位宽/功能」表）；③ 接口协议（**只写接口**：输入侧/输出侧/握手/复位/时钟，并给出可被 ⑤ 断言检查的接口不变式；**不要写内部实现与功能映射**——状态机、指针/计数器、算法、公平性推导、「给什么输入出什么输出」都归「功能描述」；**不要写组合路径延迟数字**；然后每个场景一个小标题，内容固定 = WaveDrom 图 + 文字说明） |
| 时序图 | 用 **WaveDrom** 画，**只画端口信号，不含内部状态**；至少覆盖：正常授权、多请求竞争、空请求、复位、请求中途增删；**图源 `.json` 与渲染产物 `.svg` 都放 `01-requirements/<本 REQ 文件名去扩展名>/`（与 md 同名、同级的目录）**，一个场景一对同名文件，两件都列入 `artifacts`；文字说明只讲接口信号怎么表现、需要时再加只列端口信号的逐拍表。注意：bit 信号只在电平变化处写值、其余用 `.` 保持（连写同一值会渲染出假毛刺）；图内文字用 ASCII；`head`/`foot` 过长会被截断 |
| 接口时序 | 时钟周期、输入采样沿、输出有效窗口、复位断言宽度/释放方式，逐项有值或明确待定 owner；**不写组合路径延迟** |
| 约束 | 面积/功耗/时序/工艺都要有数字或明确的待定项 owner |
| 验收标准 | `F*` 是行为契约、`AC-*` 是可观测判据，**两者分工不重复**：AC 用表格写「覆盖哪个 F + 激励 + 观测点 + 量化判据」，不要复述 F 的行为；每条 AC 都要能被一个 `TC-*` 覆盖，并引用具体场景/不变式编号 |
| non-goals | 至少写一条且覆盖软件接口、时钟域、背压/流、配置能力；不划边界，下游一定会自由发挥 |

同时把 `artifacts` 指向本阶段真实存在的支撑文件（框图、数据、参考文档），**不要填不存在的路径**。

## 自检

```bash
python3 tools/sv.py gate 01
python3 tools/sv.py trace --check
```

- 需求之间若有冲突：不要擅自裁决，列出来问用户。
- 需求若不可测：先问清楚「用什么观测手段判定通过」，再落笔。

## 完成定义

1. 已用 `grill-me`（`grilling`）与用户把边界/取舍/待定项讨论清楚，无未决问题；
2. `gate 01` 无 hard fail；
3. 每条 AC 都有明确的观测方式；
4. 软硬件接口与硬件接口都已定义（硬件接口三段式；接口协议只写接口；时序图只画端口），接口不变式可被断言检查；
5. 向用户请求放行（用 question 卡片列出 AC 与 non-goals 摘要）；
6. 用户同意后写入 `status: approved` + `reviewer` + `date`，再跑一次 `gate 01` 确认；
7. `python3 tools/sv.py trace` 更新 `INDEX.md`。

## 禁止

- 一个功能点拆成多份文件或把多条需求塞进一份文件（本仓约定：一功能点一文件）。
- 自行放行。
