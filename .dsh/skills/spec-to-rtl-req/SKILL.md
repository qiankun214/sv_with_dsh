# ① 功能点

产出**一份** `01-requirements/REQ-<nnn>-<slug>.md`，外加一份与本文件同名同级的图件目录。
它是整条追溯链的源头，必须可被下游逐条引用。上游为空（`upstream: []`），门禁 `gate 01`。

## 1. 写文档前：先 grill-me

**任何阶段文档动笔前，先用 `grill-me`（执行 `grilling` 技能）与用户做一轮质询式讨论**，把边界、取舍、待定项问清楚再落笔：

1. 先把仓内事实查清（模板、上下游产物、门禁规则、已有约定），不要拿能查到的事去问用户；
2. 加载 `grilling` 技能并按其执行：**每轮一次 `ask_user_question`**，把该轮决策点做成卡片
   （每项一个稳定 `id` 与短 `header`，推荐项放第一并标「（推荐）」+ 一句取舍说明）；
3. 讨论到「没有未决问题、且用户确认理解一致」为止；结论写进文档正文/变更历史，**不把讨论过程抄进产物**；
4. 讨论中出现的规范级结论（新的写作/结构约定）要回流到本技能或模板，别只留在当轮对话里。

## 2. 命名与目录

```
01-requirements/
├── REQ-001-clk-domain.md
├── REQ-001-clk-domain/                  # 图件目录：与本 REQ 的 md 同名、同级
│   ├── scenario-1-single-request.json
│   ├── scenario-1-single-request.svg
│   └── …
├── REQ-002-burst-split.md
└── REQ-002-burst-split/
```

- ID：`REQ-<三位序号>`，全仓唯一，**永不复用**。
- 文件名 = `ID + kebab 短描述`，排序即 ID 顺序。
- 一功能点一份文件：不把多条需求塞进一份，也不把一个功能点拆成多份。
- 新建：`python3 tools/sv.py new req --title "时钟域划分" --slug clk-domain`

## 3. front-matter（必填）

```yaml
---
id: REQ-001
title: 时钟域划分
status: draft            # draft | in_review | approved | superseded
owner: agent
reviewer:                # approved 时必填（人类）
date:                    # approved 时必填
upstream: []             # 功能点是源头，允许为空
artifacts:
  - 01-requirements/REQ-001-clk-domain/scenario-1-single-request.json
  - 01-requirements/REQ-001-clk-domain/scenario-1-single-request.svg
---
```

`artifacts` 只填本阶段真实存在的支撑文件（图件、数据、参考文档），**不要填不存在的路径**。

## 4. 正文：只写 IPO

输入（端口/参数/协议怎么给）→ 处理（`F*` 行为）→ 输出（端口/协议怎么读），外加约束与 non-goals 边界。

**章节顺序固定**：背景与目标 → 功能描述（`F*`）→ 软硬件接口 → 硬件接口 → 约束 → non-goals → 变更历史。

**不得出现验收标准 / AC 编号 / 测试判据**——「什么算通过」是 ⑤ 验证阶段的职责（见 §5 末条）。

### 4.1 背景与目标

为什么需要这个功能点、解决什么问题；一段话，不写实现方案。

### 4.2 功能描述（`F*`）

逐条编号 `F1/F2…`，每条都是**可验证的行为**（能被激励 + 观测判定），不写「高性能」「灵活」「适当」这类不可判定词。
需求之间有冲突时不要擅自裁决，列出来问用户；需求不可测时先问清「用什么观测手段判定通过」再落笔。

**按处理结果分类**：`F*` 分「正常处理流程」和「错误处理流程」两组；复位/初始化等两类流程共用的行为单独标注，不混进正常流程。分类只调整排列顺序，**`F*` 编号保持不变**。

**列举关系用列表**：一条 `F*` 里出现多项条件、字段、取值或并列动作时，用有序或无序子列表逐项列出；不要用顿号把多项内容串成一句长句。

### 4.3 软硬件接口（先给结论）

- **无软件接口**：一句结论 + 软件还能通过什么影响本模块（通常是综合期参数）+ 「要加软件接口须另立 `REQ-*`」的边界。
  **不要**列一张全「无」的表。
- **有软件接口**：详细描述寄存器/CSR、总线从接口、中断、地址空间与访问属性，并指向 `REGMAP-*`。

### 4.4 硬件接口：固定三段式

1. **参数表**：参数名、默认值、合法范围、含义。
2. **接口信息**：表头固定 `端口 | 方向 | 位宽 | 时钟域 | 复位值 | 含义`；用到结构体时另加「成员 / 位宽 / 功能」表。
3. **接口协议——只写接口**：输入侧 / 输出侧 / 握手与流控 / 复位 / 时钟，并给出可被 ⑤ 断言检查的**接口不变式**（`I1/I2…`）。
   - **不得**写内部实现与功能映射：状态机、指针/计数器、算法、公平性推导、「给什么输入出什么输出」的功能解释都归 4.2。
   - **不得**写组合路径延迟数字（如 `≤5 ns`）。
   - 接口时序（时钟周期、输入采样沿、输出有效窗口、复位断言宽度/释放方式）逐项有值，或写成「待定项 + owner」。
   - 之后每个场景一个小标题，内容固定 = **WaveDrom 图 + 文字说明**（需要时加一张只列端口信号的逐拍表）。
     至少覆盖：正常授权、多请求竞争、空请求、复位、请求中途增删。

### 4.5 约束与 non-goals

- 约束：面积/功耗/时序/工艺都要有数字，或明确的待定项 owner。
- non-goals：至少一条，且覆盖软件接口、时钟域、背压/流、配置能力。不划边界，下游一定会自由发挥。

### 4.6 变更历史

每次内容变更留痕：改了什么、为什么改、影响哪些上下游。

> **不要写「验收标准」小节**：本文档只写 IPO。验收标准（激励 / 观测点 / 量化判据）与 `TC-*`
> 由 ⑤ 从 `F*`、接口不变式与时序场景**扇出**，见 `spec-to-rtl-verify` 与 `VP.template.md`。

## 5. 时序图（WaveDrom）

- **落盘位置**：`01-requirements/<本 REQ 文件名去扩展名>/`，与 md 同名、同级。
- **一个场景一对同名文件**：`scenario-N-<场景名>.json`（图源，唯一事实源）↔ `.svg`（渲染产物，供评审直接看）。
  改图只改 `.json` 再重渲，两件同步提交，并都列入 `artifacts`。
- **只画端口信号**（如 `clk`/`rst_n`/`req_i`/`grant_o`/`grant_valid_o`），不含任何内部状态；
  内部实现与「为什么给这个授权」属于 4.2 功能描述。
- 图内只放简短 ASCII 标签；完整中文说明写在正文对应小标题下。
- 渲染（路径相对仓根；渲染器装在 `.tools/wdvenv/`，gitignored）：

  ```bash
  # 一次性准备
  python3 -m venv .tools/wdvenv && .tools/wdvenv/bin/pip install wavedrom

  .tools/wdvenv/bin/wavedrompy -i 01-requirements/<REQ 去扩展名>/scenario-2-round-robin.json \
                               -s 01-requirements/<REQ 去扩展名>/scenario-2-round-robin.svg
  ```

**三个坑（会让图「看起来对、其实错」，改图必守）**：

1. **bit 信号只在电平变化处写值，其余用 `.` 保持**。连写同一值（如 `"1100001111"`）会在每个 tick 交界渲染出假 V 形毛刺；
   bus 状态（`"2.2.2.2."`）本身用 `.` 保持，不受影响。
2. **图内文字只用 ASCII**。渲染环境不一定有中文字库（中文会变方框），中文说明写正文。
3. **`head`/`foot` 过长会被画布宽度截断**。画布宽度由 tick 数与 `hscale` 决定；本仓统一 `hscale: 1.8`，文案控制在约 60 字符内。

**记法**：每个 `clk` 周期 = 2 个 tick，顶部数字为 tick 序号，相邻两个 tick 构成一拍。
波形是需求级接口契约（如「输出以 `clk` 为基准有效」「复位期强制 0」「无请求不授权」），不约束实现细节。

## 6. 门禁与自检

```bash
python3 tools/sv.py gate 01
python3 tools/sv.py trace --check
```

- hard fail：front-matter 字段缺失/非法、ID 重复、`artifacts` 指向不存在的文件。
- warn：本阶段暂无产物；上游覆盖为空。

## 7. 放行与完成定义

1. 已用 `grill-me`（`grilling`）与用户把边界/取舍/待定项讨论清楚，无未决问题；
2. `gate 01` 无 hard fail；
3. 文档只有 IPO（输入/处理/输出 + 边界），**没有验收标准/AC/测试判据**；
4. `F*` 已按正常处理流程/错误处理流程分类，复位/初始化等共用行为单独标注；列举关系已用有序或无序列表；
5. 软硬件接口与硬件接口都已定义（三段式；接口协议只写接口；时序图只画端口），接口不变式可被断言检查；
6. 向用户请求放行（用 question 卡片列出 `F*`、接口结论与 non-goals 摘要）；
7. 用户同意后写入 `status: approved` + `reviewer` + `date`，再跑一次 `gate 01` 确认；
8. `python3 tools/sv.py trace` 更新 `INDEX.md`。

放行后该 REQ 才能被 ② 引用。**`reviewer` 只能是真实人类**；样例数据必须显式标注为样例评审。
返工即作废原放行（`approved` → `in_review`，清空 `reviewer`）。

## 8. 禁止

- 一个功能点拆成多份文件，或把多条需求塞进一份文件。
- 把功能点写成流水账，或把多项条件/字段/取值塞进一句用顿号连接的长句。
- 为了分类重编号 `F*`；分类只调整排列顺序。
- 在本文档写验收标准 / AC / 测试判据（那是 ⑤ 的职责）。
- 在接口协议里写内部实现、功能映射或组合路径延迟。
- 自行放行，或代填 `reviewer`。
