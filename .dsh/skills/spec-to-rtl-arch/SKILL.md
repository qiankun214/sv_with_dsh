# ② 系统方案

产出 `02-architecture/ARCH-<nnn>-<slug>.md`，上游必须是**已 approved** 的 `REQ-*`。

## 文档必须由 `grill-me` 讨论产出（强制）

**本阶段文档不允许「先写完再评审」**：必须先用 `grill-me`（执行 `grilling` 技能）与用户逐轮质询式讨论，
把方案问到完善，再落成 `ARCH-*`。讨论是产出文档的**必经过程**，不是可选项。

- **事实自己查**：模板、上游 `REQ-*`、`tools/sv.py` 规则、`standards/`、已有 ARCH/DES——能查到的不要拿去问用户；
  已定决策涉及的文档要重读，发现矛盾先报告、不要在过时结论上继续；
- **每轮一次 `ask_user_question`**：把该轮决策点做成卡片（稳定 `id` + 短 `header`，推荐项放第一并标「（推荐）」+ 一句取舍说明），
  用户也可以直接写自己的答案；不要用散文复述选项，也不要一次抛一堆散问题；
- 讨论到**没有未决问题、每一节都能落下确定内容**为止。

**「完善」的判定（缺一不可）**：

1. 正文没有任何 `TODO` / `<占位>` / 「待定」「后面再说」式的表述；
2. 每个必填小节都有确定内容；面积/频率/延迟/位宽等数字**有值**，或写成「待定项 + owner + 期限」；
3. 上游每个 `REQ-*` 都能在「功能点覆盖」里找到落点；上下游冲突已在讨论中显式裁决（未裁决就回 ① 问用户）；
4. **功能分解为模块无歧义**：每个 module 的预计 RTL **≤ 500 行**——超过 500 行必须继续拆；单模块就够时**不要为拆而拆**；
   module 职责、边界与模块间连接写清；module 名与后续 `03-design/<module>/` 目录名一致；
   `id_short`（2–8 位 `[a-z][a-z0-9_]`、全仓唯一）等契约字段已想清楚；
5. 图件按「图源与渲染放与本文件**同名、同级**的目录」入库并登记进 `artifacts`；
   时序类图用 **WaveDrom**（沿用 REQ 的三个坑：点记法保持、图内 ASCII、控制标题长度）；
6. 用户逐节确认过，并明确同意放行。

结论写进产物正文与变更历史；**不要把问答过程抄进产物**。讨论中形成的规范级结论必须回流到本技能或模板。

## 步骤

```bash
python3 tools/sv.py new arch --title "总线协议方案" --slug bus-protocol
```

必填内容与判断标准（写不出来就是没设计完）：

| 小节 | 判断标准（写不出来就是没设计完） |
|---|---|
| 方案概述 | 一句话方案 + 一张框图（图件放与本文件同名的目录，见上） |
| 整体架构 | 系统总体结构：由哪些 module 组成、数据流/控制流怎么走、时钟/复位如何贯穿；配**模块级**框图（不画 module 内部） |
| 功能点覆盖 | 每个声明的 `REQ-*` 都能在方案里找到实现路径 |
| 功能分解为模块 | 把功能分解到 module：**每个 module 预计 RTL ≤ 500 行**（超过就必须继续拆）；写清每个 module 的职责与不做什么、划分依据（含「为何不继续拆」）；module 名即后续 `03-design/<module>/` 的目录名 |
| 模块间连接 | 模块之间怎么连：连接框图（谁连谁、什么信号）+ **模块间接口表**（信号/方向/位宽/说明）；只有一个 module 时写明「无模块间连接」 |
| 接口与协议 | **端口表以 `REQ-*` 为唯一权威，本文件不要重复抄写**；这里只描述模块间接口、握手的位宽/字节序，以及软硬件接口的结论（与 ① 一致） |
| 时钟与复位 | 时钟域清单 + 跨域策略；写「后面再说」视为未完成 |
| 资源与时序预算 | 面积（sky130 单元数量级）、频率、延迟都要有数；并写明综合与回归的参数档位；⑥ 阶段会拿它对照 |
| 取舍与被否方案 | 至少一条，写清否决理由，避免下游重复讨论 |
| 变更历史 | 每次内容变更都留痕（改了什么、为什么、影响谁） |

> **本阶段不做 module 内部设计**：内部功能块划分、FSM、数据通路、位宽推导、寄存器清单都属于 ③ 详细设计，
> `ARCH-*` 只把「功能 → module → module 间连接」定清楚。框图也只画到 module 边界。

**本阶段不要创建模块骨架。** `new module` 会同时建 `03/04/05` 三处目录，而门禁规则是
「`04-rtl/<module>/` 存在 ⇒ 同模块必须有 approved 的 `DES-*`」——在 ② 阶段建骨架会让 `gate 02` **立刻 hard fail**。
骨架在 ③ 阶段与 `DES-*` 一起创建（一次性走完 `new module → new des → 写 DES → 放行`）：

```bash
# 在 ③ 阶段执行，不要在 ② 放行前执行
python3 tools/sv.py new module dma --short dma
```

## 自检

```bash
python3 tools/sv.py gate 02
```

- 若发现某功能点无法被任何方案满足：**回到 ① 与用户确认**，不要默默改需求。
- 预案中的预算若明显不可达（如频率超出工艺），先暴露矛盾再放行。

## 完成定义

1. **已通过 `grill-me` 讨论**，且达到上面的「完善」判定（无 TODO/占位，数字有值或显式待定项）；
2. `gate 02` 无 hard fail；
3. 每个声明的 `REQ-*` 都能在方案中找到落点；功能分解后每个 module 预计 RTL ≤ 500 行；模块间连接无歧义；被否方案有理由；
4. 向用户请求放行（列出功能分解与模块间连接、资源/时序预算）；
5. 放行后写 `status: approved` + `reviewer` + `date`；
6. `python3 tools/sv.py trace` 更新 `INDEX.md`。

## 禁止

- 跳过 `grill-me` 讨论直接写文档，或把 `TODO`/「待定」留在正文里当交付。
- 为拆而拆：功能总量低于 500 行时硬分子模块；或反过来，预计超过 500 行还不拆。
- 在 ② 定义 module 内部结构（内部功能块、FSM、数据通路、寄存器清单）——那是 ③ 的事。
- 在 ② 重复抄写 `REQ-*` 的端口表（接口以 ① 为唯一权威）。
- 在 ② 阶段创建 `03/04/05` 模块骨架（会让 `gate 02` hard fail）。
- 自行放行（`reviewer` 只能是真实人类）。
