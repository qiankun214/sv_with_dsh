# ② 系统方案

产出 `02-architecture/ARCH-<nnn>-<slug>.md` + 同名同级的图件目录。上游必须是**已 approved** 的 `REQ-*`，门禁 `gate 02`。

本阶段只回答三件事：**整体架构 → 功能如何分解为 module → 模块之间怎么连**。
目标是把功能分解为**每个不超过 500 行 RTL 的 module**：超过 500 行必须继续拆，远低于则不为拆而拆。
**不设计 module 内部结构**（功能块、FSM、数据通路、寄存器清单）——那是 ③ 的职责；
也**不重复抄写 `REQ-*` 的端口表**——接口以 ① 为唯一权威。

## 1. 文档必须由 grill-me 讨论产出（强制）

**不允许「先写完再评审」**：先用 `grill-me`（执行 `grilling` 技能）与用户逐轮质询式讨论，把方案问到完善，再落成 `ARCH-*`。

- **事实自己查**：模板、上游 `REQ-*`、`tools/sv.py` 规则、`standards/`、已有 ARCH/DES——能查到的不要拿去问用户；
  已定决策涉及的文档要重读，发现矛盾先报告、不要在过时结论上继续；
- **每轮一次 `ask_user_question`**：决策点做成卡片（稳定 `id` + 短 `header`，推荐项放第一并标「（推荐）」+ 一句取舍说明），
  用户也可以直接写答案；不要用散文复述选项，也不要一次抛一堆散问题；
- 讨论到**没有未决问题、每一节都能落下确定内容**为止。

**「完善」的判定（缺一不可）**：

1. 正文没有任何 `TODO` / `<占位>` / 「待定」「后面再说」式表述；
2. 每个必填小节都有确定内容；面积/频率/延迟/位宽等数字**有值**，或写成「待定项 + owner + 期限」；
3. 上游每个 `REQ-*` 都能在「功能点覆盖」里找到落点；上下游冲突已在讨论中显式裁决（未裁决就回 ① 问用户）；
4. **功能分解为模块无歧义**：每个 module 的预计 RTL **≤ 500 行**，超过继续拆，单模块够时不为拆而拆；
   module 职责、边界与模块间连接写清；module 名与后续 `03-design/<module>/` 目录名一致；
   `id_short`（2–8 位 `[a-z][a-z0-9_]`、全仓唯一）等契约字段已想清楚；
5. 图件按「图源与渲染放与本文件**同名、同级**的目录」入库并登记进 `artifacts`；
   时序类图用 **WaveDrom**（沿用 ① 的三个坑：点记法保持、图内 ASCII、控制标题长度）；
6. 用户逐节确认过，并明确同意放行；
7. **没有废话与重复**：上游已有内容用引用标记（如「见 `REQ-001` 硬件接口」）而非重述/复制表格；
   正文只留本阶段新结论——功能分解、各模块功能、模块间连接，以及预算与参数/验证口径。

结论写进产物正文与变更历史；**不把问答过程抄进产物**。规范级结论必须回流到本技能或模板。

## 4. 正文该写什么

| 小节 | 判断标准（写不出来就是没设计完） |
|---|---|
| 方案概述 | 一句话方案 + 一张**模块级**框图（只画到 module 边界） |
| 整体架构 | 由哪些 module 组成、数据流/控制流怎么走、时钟/复位如何贯穿 |
| 功能点覆盖 | 每个声明的 `REQ-*` 都能在方案里找到实现路径 |
| 功能分解为模块 | 每个 module 做什么 / 不做什么、预计 RTL 行数（≤500）、划分依据（含「为何不继续拆」）；module 名即后续 `03-design/<module>/` 的目录名 |
| 模块间连接 | 连接框图 + **模块间接口表**（信号/方向/位宽/说明）；只有一个 module 时写明「无模块间连接」 |
| 接口与协议 | **端口表以 `REQ-*` 为唯一权威，不重复抄写**；只写模块间接口、握手的位宽/字节序，以及软硬件接口结论（与 ① 一致） |
| 上游引用（不重述） | 功能点覆盖、端口、接口协议、时钟复位、时序约束 → 用引用标记指向 `REQ-*` 出处，不重述、不复制表格 |
| 资源与时序预算 | 只写本阶段新增的数字（如面积预算、频率、延迟）与口径（综合/回归参数档位、验证深度）；沿用上游的指标用引用 |
| 取舍与被否方案 | 至少一条，写清否决理由，避免下游重复讨论 |
| 变更历史 | 每次内容变更留痕（改了什么、为什么、影响谁） |

> **不做 module 内部设计**：内部功能块划分、FSM、数据通路、位宽推导、寄存器清单都属于 ③；
> `ARCH-*` 只把「功能 → module → module 间连接」定清楚，框图也只画到 module 边界。

## 5. 图件布局

- 图源与渲染产物放 `02-architecture/<本 ARCH 文件名去扩展名>/`，与本文件的 `.md` **同名、同级**；
- 结构框图用 **Mermaid + ASCII**（`.md`），渲染由 Markdown 预览器完成，无需额外工具链；
- 时序类图用 **WaveDrom**（`.json` 图源 + `.svg` 渲染），规则同 ①：点记法保持、图内 ASCII、控制标题长度；
- 两件都入库并列入 front-matter 的 `artifacts`；
- 端口与信号语义以 `REQ-*` 为唯一权威，图件目录不重复维护。

## 6. 步骤与骨架时序坑

```bash
python3 tools/sv.py new arch --title "总线协议方案" --slug bus-protocol
```

**本阶段不要创建模块骨架。** `new module` 会同时建 `03/04/05` 三处目录，而门禁规则是
「`04-rtl/<module>/` 存在 ⇒ 同模块必须有 approved 的 `DES-*`」——在 ② 阶段建骨架会让 `gate 02` **立刻 hard fail**。
骨架在 ③ 阶段与 `DES-*` 一起创建（一次性走完 `new module → new des → 写 DES → 放行`）：

```bash
# 在 ③ 阶段执行，不要在 ② 放行前执行
python3 tools/sv.py new module dma --short dma
```

## 7. 门禁与自检

```bash
python3 tools/sv.py gate 02
```

- hard fail：上游 `REQ-*` 不存在或未 `approved`；字段缺失；`artifacts` 路径不存在。
- warn：本阶段暂无产物。
- 若发现某功能点无法被任何方案满足：**回到 ① 与用户确认**，不要默默改需求。
- 预算若明显不可达（如频率超出工艺），先暴露矛盾再放行。

## 8. 放行与完成定义

1. **已通过 `grill-me` 讨论**，且达到 §1 的「完善」判定；
2. `gate 02` 无 hard fail；
3. 每个声明的 `REQ-*` 都有落点；功能分解后每个 module 预计 RTL ≤ 500 行；模块间连接无歧义；被否方案有理由；
4. 向用户请求放行（列出功能分解、模块间连接、资源/时序预算）；
5. 用户确认后写 `status: approved` + `reviewer` + `date`；
6. `python3 tools/sv.py trace` 更新 `INDEX.md`。

放行后 ③ 才能开工。**`reviewer` 只能是真实人类。**

## 9. 禁止

- 跳过 `grill-me` 讨论直接写文档，或把 `TODO`/「待定」留在正文里当交付。
- 为拆而拆：功能总量低于 500 行时硬分子模块；或反过来，预计超过 500 行还不拆。
- 在 ② 定义 module 内部结构（功能块、FSM、数据通路、寄存器清单）。
- 在 ② 重复抄写 `REQ-*` 的端口表。
- 在 ② 阶段创建 `03/04/05` 模块骨架（会让 `gate 02` hard fail）。
- 自行放行（`reviewer` 只能是真实人类）。
